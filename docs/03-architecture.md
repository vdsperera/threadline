# Architecture Design — Threadline

## 1. Component Map

### 1.1 Visual CMS (Sveltia CMS)
- **Name**: Visual CMS
- **Responsibility**: Provides the GUI for Content Creators to authenticate, manage case metadata, and add/edit events visually.
- **Exposes**: Interactive UI on the `/admin/` route.
- **Depends on**: GitHub API (for authentication and committing changes).
- **Data owned**: None directly (stateless client-side application).
- **Technology**: Sveltia CMS (Git-backed headless CMS) — chosen because it requires no database and runs entirely in the browser communicating with GitHub API.
- **Scaling strategy**: Horizontally scales via CDN (GitHub Pages). Processing is done on the client.
- **Failure mode**: If GitHub API goes down, the CMS gracefully degrades by allowing local staging but preventing saving/publishing.

### 1.2 Git Storage Backend
- **Name**: Git Storage
- **Responsibility**: Serves as the single source of truth for all case data stored as flat `.json` files.
- **Exposes**: Git repository interface, GitHub API endpoints.
- **Depends on**: None.
- **Data owned**: Case metadata and Timeline events.
- **Technology**: GitHub Repository — chosen for version control, zero hosting cost, and native CI/CD integration.
- **Scaling strategy**: Handled by GitHub's infrastructure.
- **Failure mode**: If GitHub is unavailable, editing and deploying are blocked, but the live site remains up.

### 1.3 SSG Builder (Astro)
- **Name**: SSG Builder
- **Responsibility**: Parses case JSON files and generates static HTML case pages with chronological event layouts.
- **Exposes**: CLI commands (`astro build`).
- **Depends on**: Git Storage (reads `cases/*.json`).
- **Data owned**: None.
- **Technology**: Astro — chosen for its SSG capabilities and default zero-JS output.
- **Scaling strategy**: Build times can be parallelized; currently runs in GitHub Actions.
- **Failure mode**: If a build fails due to malformed JSON, the pipeline stops and the old production version remains live (hard failure on build, graceful fallback for production).

### 1.4 Client-Side Timeline Filter
- **Name**: Timeline Filter
- **Responsibility**: Instantly filters rendered events on the frontend by category or person without a page reload.
- **Exposes**: DOM event listeners on filter buttons.
- **Depends on**: DOM structure generated by SSG Builder.
- **Data owned**: Client-side UI state (active filters).
- **Technology**: Vanilla JavaScript — chosen to maintain zero-JS framework overhead and maximize performance.
- **Scaling strategy**: N/A (Client-side execution on small DOM subsets).
- **Failure mode**: If JS is disabled by the reader, the page gracefully degrades by showing all events (no filtering, but fully readable).

### 1.5 CI/CD Pipeline
- **Name**: CI/CD Pipeline
- **Responsibility**: Listens for commits to `main`, triggers the Astro build, and publishes to GitHub Pages.
- **Exposes**: GitHub Actions Workflow.
- **Depends on**: GitHub Webhooks, SSG Builder.
- **Data owned**: Build logs and artifacts.
- **Technology**: GitHub Actions — chosen for native integration and no additional cost.
- **Scaling strategy**: GitHub Actions provides concurrent runners if needed.
- **Failure mode**: Build failures send alerts to contributors; production is not updated.

## 2. API Contracts

*Note: Threadline uses a Git-backed architecture. There are no proprietary backend APIs.*

### 2.1 CMS to GitHub API (Commit Workflow)
- **Method / Endpoint**: `PUT /repos/{owner}/{repo}/contents/{path}`
- **Request shape**: JSON containing `message`, `content` (base64 encoded case `.json`), and `sha`.
- **Response shape**: GitHub commit details and file metadata.
- **Error codes**: `401 Unauthorized` (invalid PAT), `409 Conflict` (stale `sha`), `422 Unprocessable Entity`.
- **Auth requirement**: GitHub Personal Access Token (PAT).
- **Idempotency**: Handled via `sha` (optimistic concurrency).

## 3. Data Models

### 3.1 Case Entity (JSON)
- **Key fields**: `id`, `title`, `location`, `years`, `dek`, `cardBlurb`, `source`, `statusBadge`
- **Relationships**: Contains an array of `events`, and a map of `persons`.
- **Storage technology**: Flat `.json` file in `cases/` directory.
- **Data ownership**: Git Storage Backend.

### 3.2 Person Entity (JSON Map)
- **Key fields**: `personkey` (ID), `name`, `role`, `status`, `statusColor`
- **Relationships**: Referenced by events.
- **Storage technology**: Embedded within the Case Entity JSON.
- **Data ownership**: Git Storage Backend.

### 3.3 Event Entity (JSON Array Item)
- **Key fields**: `year`, `date`, `cat`, `title`, `summary`, `detail`, `quote`
- **Relationships**: Contains array of `persons` references.
- **Storage technology**: Embedded within the Case Entity JSON.
- **Data ownership**: Git Storage Backend.

## 4. NFR Mapping

| Non-Functional Requirement | Architectural Decision |
|---------------------------|------------------------|
| **NFR-001**: Maximum performance / Fast page loads | Use Astro for Static Site Generation (SSG). |
| **NFR-002**: Zero-database / Low maintenance cost | Store all data as flat `.json` files in GitHub. |
| **NFR-003**: Zero-JS framework overhead | Use vanilla JS for the client-side interactive filter. |
| **NFR-004**: Secure CMS access without custom auth | Delegate auth to GitHub via Personal Access Tokens. |

## 5. Risk Flags

- **Single point of failure with no fallback**: 
  - *Risk*: GitHub API outages.
  - *Consequence*: Content creators cannot save or publish changes.
  - *Mitigation*: Unavoidable trade-off for zero-DB architecture. Sveltia CMS caches drafts in local storage so work is not lost.
- **Undefined data migration path for existing schema**:
  - *Risk*: If the JSON schema changes in the future, existing cases might break the build.
  - *Consequence*: SSG Builder fails.
  - *Mitigation*: Implement Zod schema validation during the Astro build step to catch mismatches.

## 6. Architecture Decision Records (ADRs)

### ADR-001
**Title**: Use Git-backed JSON instead of a Database
**Status**: Accepted
**Context**: We need to store complex case data. Traditional CMSs require Postgres/MySQL, adding cost and maintenance.
**Options considered**: 
1. Supabase/Postgres
2. Firebase
3. Git-backed flat JSON files
**Decision**: Git-backed flat JSON files via Sveltia CMS.
**Consequences**: Easier hosting (free), built-in version control, but eliminates the ability to do complex server-side relational queries (which we don't need since cases are self-contained).

### ADR-002
**Title**: Use Vanilla JS for Timeline Filtering
**Status**: Accepted
**Context**: Readers need to filter case events instantly.
**Options considered**:
1. Server-side rendering (SSR) on query params
2. Heavy framework (React/Svelte island)
3. Vanilla JS DOM manipulation
**Decision**: Vanilla JS DOM manipulation.
**Consequences**: Keeps page size minimal and respects the "Zero-JS overhead" requirement, but requires careful DOM event listener management.
